# Career Mode Capstone: Portfolio Case Study

Turn a project or work sample into clear, credible portfolio evidence. Practice a reviewable Git history, document your decisions, publish a release, and prepare an interview story grounded in the work.

This repository is a DevFlow Academy starter. Fork it to your own GitHub account, then complete the six milestones in the academy's **Career Mode** capstone guide.

## Project brief

Choose a project you built, a permitted work sample, or a new small project. Explain the problem, your contribution, the constraints, the decisions you made, and the outcome. A hiring manager should be able to understand the work from the repository without needing access to private systems.

## Getting started

1. Select **Fork** on this repository's GitHub page.
2. Clone your fork, replacing `<YOUR-USERNAME>` with your GitHub username:

   ```sh
   git clone https://github.com/<YOUR-USERNAME>/devflow-career-capstone.git
   cd devflow-career-capstone
   ```

3. Replace the starter text below with a specific, truthful summary:

   > Case study focus: [choose a project and target role]

## Milestones

### 1. Define your evidence

- Open a GitHub issue describing the project or work sample you will present.
- Create `CASE_STUDY.md` with:
  - the problem and intended users;
  - your role and what you personally delivered;
  - constraints, tools, and important decisions;
  - the outcome and what you would improve next.
- Link a demo or screenshots only when you have permission to share them.

### 2. Build a reviewable change

- Create a branch named `feature/case-study`.
- Add the case study and any permitted work sample or project documentation.
- Use focused commits with messages that explain the change.
- Open a pull request to your fork's `main` and review it as an employer would.

### 3. Practice a documentation conflict

1. Create two branches from the same `main` commit.
2. On the first branch, update the `Case study focus` line in this README with your target role.
3. On the second branch, update that same line with your project outcome.
4. Merge the first branch into the second, resolve the README conflict, and commit a single clear final description.

### 4. Polish and release

- Check your links, spelling, screenshots, commit history, and public-data safety.
- Request peer feedback if possible, then merge the reviewed pull request.
- Tag `v1.0.0`, create a short release description, and add relevant repository topics.

### 5. Prepare your interview story

- Write `INTERVIEW_STORY.md` using Situation, Task, Action, and Result.
- Ground the story in decisions and outcomes visible in this project; do not make unsupported claims.
- Practice a concise answer and link it from the case study if useful.

## Completion checklist

- [ ] The issue and case study make the project's purpose, your role, and its outcome clear.
- [ ] The pull request and commit history are focused and understandable.
- [ ] The documentation conflict was resolved into one consistent story.
- [ ] The repository has a `v1.0.0` release and an interview-ready STAR story.
- [ ] Everything in the public repository is yours to share.

## Privacy and accuracy

Do not publish employer or client code, private data, confidential metrics, or identifiable details without permission. Clearly distinguish your own contribution from work completed by a team.
